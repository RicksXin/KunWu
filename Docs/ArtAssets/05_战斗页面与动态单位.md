# 5. 战斗页面与动态单位

版本：0.2\
日期：2026-08-03\
状态：美术制作唯一事实源分册\
上级索引：[《昆吾禁地》美术素材制作总清单](README.md)

本分册集中记录战斗页面背景、动态战斗立绘、单位信息覆盖层、技能与状态图标、战斗特效的
素材规格、参考截图和 GPT Image 提示词。战斗数值与行动规则以
[PRD-04](../PRD/04_编队战斗与技能策略_PRD.md) 为准，页面信息层级与交互以
[PRD-09 §7](../PRD/09_UI交互与新手引导_PRD.md#7-战斗ui) 为准，动画帧数、事件帧与导入方式以
[动画制作规范](../04_动画制作规范.md) 为准。

## 5.1 已确认的画面规则

- 玩家可见窗口与 UI 唯一设计基准为 `375×817`；此前口述的 `385×817` 不作为制作尺寸。
- 页面底部至少保留 `54px` 安全区；我方修士不得压入该区域。
- 普通敌群位于中上方并排显示；首领居中，召唤单位可采用三角阵或环绕阵。阵型只影响
  视觉排版，不产生前后排、距离或承伤规则。
- 我方最多四名修士位于底部安全区上方并排显示。
- 敌我双方都使用动态战斗立绘。技能释放、受击、治疗和阵亡必须有相应人物动作或特效反馈。
- 页面只提供正常速度，不显示或预留 `2×` 按钮。
- 达到战斗配置规定的生命阈值或剧情条件时，右上角显示“逃生”；未满足条件时不显示禁用
  占位。
- 所有角色名、技能名、生命数字、伤害/治疗数字和状态层数都由 Cocos Label 与本地化表
  渲染，不得烘焙进 PNG。

### 5.1.1 单位信息顺序

敌方单位从上到下固定为：

```text
动态立绘
名称
族类图标 + 生命条
行动条
状态图标
```

我方修士使用相同顺序。敌我差异通过名称颜色、生命条颜色和自动施法标记表达，不改变
信息位置。

“名称、族类图标 + 生命条、行动条、状态图标”不是立绘外的独立纵向区域，而是全部
覆盖在动态立绘底部。标准单位立绘逻辑框暂定 `86×205`；底部 `56px` 为信息覆盖区，
人物仍可在该区域后方显示，但服装纹样、武器尖端和关键动作剪影不得只依赖这一区域辨认。

标准单位覆盖区自上而下建议按以下尺寸合成；这是素材制作和 Prefab 初始布局基线，后续
可以在 Cocos Creator 中微调位置，不应因此重新生成角色图：

| 信息         | 逻辑高度 | 布局要求                                  |
| ---------- | ---: | ------------------------------------- |
| 名称         | `12` | 水平居中；敌方在暖白描边，我方在青白描边；点击我方名称切换自动施法     |
| 族类图标 + 生命条 | `10` | `12×12` 图标在左，生命条在右；数字由 Label 覆盖在条内或上方 |
| 行动条        |  `5` | 与生命条右侧对齐；填充比例由代码控制                    |
| 状态图标       | `14` | 从左向右排列，超出当前可见数量时显示“+n”Label，不缩小图标     |
| 行间距与安全边    | `15` | 分散到各行之间及底部，避免像素贴边                     |

普通敌群与四人队伍都使用同一套覆盖层组件。首领立绘可以扩大到逻辑 `172×256`，但信息
覆盖层只在立绘底部居中扩展到最多 `112×60`，不能把条形 UI 等比放大到遮住主体。

## 5.2 动态立绘的实际交付口径

用户口述的“Live2D 动态立绘”在本分册中先统一称为“动态战斗立绘”，避免把视觉效果与
某一种运行时技术绑定。当前工程尚未接入 Live2D Cubism，现有事实源规定 Demo 战斗单位
采用单方向 Sprite Sheet 与 Cocos `AnimationClip`：

| 路线                           | 本阶段是否采用 | GPT Image 能提供什么                           | 仍需人工/工具完成什么                                                             |
| ---------------------------- | ------- | ----------------------------------------- | ----------------------------------------------------------------------- |
| Sprite Sheet + AnimationClip | 是       | `@3x` 角色母版、统一造型、Idle/三个技能/受击/阵亡关键姿势、特效关键帧 | 像素清稿、降至运行时 `@1x`、中间帧、锚点、挂点、图集、JSON、AnimationClip 与事件帧                   |
| Live2D Cubism                | 否，待单独确认 | 分层拆件前的角色设定母版                              | 分层 PSD、`.moc3`、`.model3.json`、纹理图集、physics/pose、Motion、SDK、Web 运行时与许可设计 |

因此不得把 GPT Image 生成的一张“角色会动的效果图”登记为已完成动画。每名动态单位只有
同时交付 Idle、三个技能动作、Hurt、Death、帧数据与事件帧，才算完成本阶段战斗动画包。

## 5.5 不需要单独出图的内容

| 内容                  | 实现方式                                  |
| ------------------- | ------------------------------------- |
| 角色名、敌人名、技能名、生命数字    | Ark Pixel/Cocos Label + 本地化表          |
| 伤害数字、治疗数字、状态层数和剩余时间 | Label、对象池和 Tween；伤害与治疗用符号/颜色双重区分      |
| 生命与行动填充比例           | Sprite Mask、Fill Range 或裁切，不生成每档百分比图片 |
| 技能冷却遮罩与倒计时          | Cocos 灰度/扇形遮罩 + Label                 |
| 技能按钮按下、禁用           | `100ms` 缩放、Tint、透明度；有效触控区至少 `48×48dp` |
| 普通敌群、三角阵、环绕阵        | 布局配置，不制作阵型背景图                         |
| 受击闪白、轻微位移、屏幕震动      | Cocos Tween/材质，不烘焙进特效图                |
| 信息覆盖层中的文字描边         | Label Outline/Shadow，不生成带字名称牌         |

## 5.6 GPT Image 共用提示词与生成规则

每条具体提示词都应包含以下字段，避免只写一句风格描述：

```text
Use case：用于《昆吾禁地》375×817竖屏战斗页面的正式可切图美术资产。
```

## 5.14 推荐制作顺序

1. 先搭 Combat 灰盒，导出单敌、敌群、技能就绪和单位覆盖层四张 `375×817` 截图。
2. 人工检查四张旧入山立绘中的同质化问题，但不把它们上传给 GPT；直接使用 §5.8.1
   的文字矩阵生成四人差异设定板，按性别、年龄感、肤色、脸型、发型、体型、配饰和
   灰度剪影逐项验收，通过后裁出四张单人身份参考。
3. 生成并接入背景，确认敌我立绘区域的明暗对比。
4. 按 §5.3.1 上传石岩身份参考及两张项目截图，与残禁石傀分别制作 Idle 母版；合成单位
   信息覆盖层，验证底部 `56px` 不遮脸、职业器物和关键动作。
5. 完成生命条、行动条、族类图标和状态图标，在 `86×205` 单位槽内检查实际可读性。
6. 石岩和石傀的完整动画包通过后，再从各自身份参考出发完成陆清、白灵、墨言，不得
   复制石岩的脸、体型、发型或服装结构。
7. 用已批准身份参考回补入山卡面，保证编队与战斗中同一修士保持同一张脸和身体特征。
8. 先制作十二个炼气技能图标，各取一个角色完成三图小组，确认同角色三个技能能靠剪影区分；
   再按 §5.10.3 补齐八个筑基分支的二十四个技能图标，并将全部三十六张放入对照板检查。
9. 以技能动作的 `cast_commit/hit_frame` 为基线制作通用受击、治疗和十二套技能特效。
10. 最后制作自动施法与逃生入口，并检查不满足逃生条件时页面不存在空按钮。
