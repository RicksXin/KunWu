## 1. 为什么独立

0.1 Demo 的目标是尽快验证“玩家能否顺畅完成一次有趣的核心循环”，1.0 正式版本则要
落地前四章、招贤馆、完整职业成长、长期数值、正式资产、兼容性和发布质量。两者共用同一套产品
规则与代码基础，但不得再共用一份待办清单，否则正式版需求会持续挤占可体验闭环。

本目录只管理 0.1 Demo 的范围裁剪、技术交付、接口、进度和验收。1.0 产品规则由
[`Docs/1.0策划案/`](../1.0策划案/)单向派生至[`Docs/PRD/`](../PRD/)；Demo 文档只能选择
和裁剪已确认规则，不能反向改写 1.0 策划或 PRD。

## 2. 0.1 Demo 的两个内部交付点

D0/D1 是 0.1 Demo 的内部制作阶段，不是独立产品版本号，也不进入 1.0 PRD 的需求编号。

| 0.1内部交付点 | 目标 |
|---|---|
| D0 可玩样机 | localhost完成15–20分钟“营地—入山—探索—战斗—回城”闭环 |
| D1 公开切片 | 形成30–45分钟可独立展示、可公开分发的Demo |

D0 未通过前，不推进 D1 的内容扩充；D1 未通过前，不进入 1.0 前四章正式版本制作。

## 4. 事实源与维护规则

- 产品规则冲突：按`Docs/1.0策划案/ → Docs/PRD/`单向事实源处理。
- Demo 范围冲突：以本目录的 `01_Demo范围与体验闭环.md` 为准。
- Demo 当前进度冲突：只以 `05_Demo开发进度与待办.md` 为准。
- Demo 验收冲突：以 `06_Demo验收与发布.md` 为准。
- Demo 模块进入开发前只要求产品范围、客户端状态流、存档/失败恢复和人工验收口径明确；
  不强制服务端设计、API 契约或 Local Adapter。已有 API First 模块可以继续使用原实现。
- 正式项目的 P3/P4 内容不得写入 Demo 待办；只能记录为“Demo 后续依赖”的链接。
- Demo 完成项必须以玩家能从 localhost 进入、操作、返回和恢复存档为准，代码或单测存在
  不等于可体验。
