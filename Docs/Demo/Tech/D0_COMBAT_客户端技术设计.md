# D0 固定遭遇战客户端技术设计

版本：1.1  
日期：2026-08-03  
范围：D0 灰盒战斗闭环

## 1. 目标与边界

D0 只实现首张地图「残禁石傀」固定遭遇战：玩家从地图事件面板选择“迎战”，观看
20 Hz 时间轴战斗，手动选择技能或切换自动施法，并在胜利、逃生、战败或僵持后得到
稳定结果。

- UI 逻辑基准为 `375×817`，只提供正常速度。
- 四名初始修士使用营地已有静态立绘；敌人、背景和特效允许使用 Graphics 灰盒。
- Demo 战斗单位固定使用静态立绘，不接入 Live2D，也不制作角色逐帧动作；技能及通用战斗
  特效后续使用 Sprite Sheet + Cocos `AnimationClip`。正式 Combat 场景资源、Boss 阵形和
  完整回城结算不属于本条。
- Demo 阶段不建立 API Port 或 Local Adapter；结算仍通过 Application Service 更新状态。
- 美术替换规格见[战斗页面与动态单位美术分册](../../ArtAssets/05_战斗页面与动态单位.md)。

## 2. 页面宿主与路由

D0 不手写新的场景 UUID。逻辑路由仍使用独立的 `pageId: combat`，物理上暂时复用
`Map.scene` 作为宿主：

```text
地图事件面板
→ router.push(combat, { mapId, objectId, enemyId })
→ Map.scene 加载
→ MapPresenter 识别 combat 路由
→ 安装 CombatPresenter，并创建运行时 375×817 战斗节点树
```

这样不会让表现层反向进入地图业务。D1 若创建正式 `Combat.scene`，只需修改路由场景映射
并将同一个 `CombatPresenter` 挂入新场景，领域结算器和应用服务无需改写。

场景或配置加载失败时，路由撤销刚压入的 combat 记录，页面提供返回地图入口；不得留下
不可返回的空白页。

## 3. 状态流

```text
CombatPresenter
→ CombatApplicationService.start(context, combat_d0.json)
→ 创建 CombatSnapshot
→ 每 0.05 秒提交一次 advance
→ CombatResolver 产出新 Snapshot + CombatEvent[]
→ Presenter 先刷新单位数据，再由 CombatEventPlayer 播放表现
```

表现层只提交 `useSkill`、`toggleAuto`、`escape` 等意图，不直接修改生命、行动条、状态或
伤害结果。战斗继续保持：

```text
CombatCommand → CombatResolver → CombatEvent → 表现层
```

固定数值来自 `assets/bundles/shared/combat_d0.json`。D0 配置包括四名修士初始行动计时、
15 个技能、残禁石傀属性、35% 逃生阈值、`200` 魂晶奖励和 1 个辟谷饼掉落。

## 4. 输入与表现

- 手动修士行动计时归零时进入 `manualReadyQueue`。队首显示三个技能；同 tick 就绪者按
  `unitId` 稳定排序入队，不同 tick 严格保留先到先出顺序。
- 队首尚未释放技能时，后续修士不得替换技能面板。所有等待中的手动修士
  `actionTimer` 保持为 `0`，不设置超时自动施法；玩家选择技能，或主动切换自动并完成
  本次自动施法后才出队。
- 点击我方名称切换“手动/自动”；自动单位行动条满后按技能定义顺序选择首个合法技能。
- 敌方行动条满后按配置自动选择技能。
- 敌我信息均覆盖在立绘底部，顺序为“名称 → 族类图标 + 生命条 → 行动条 → 状态图标”。
- `CombatEvent` 驱动技能名称、伤害/治疗数字、静态立绘受击位移、出招缩放、状态文字和
  阵亡变暗；接入正式素材后，同一事件再触发对应 Sprite Sheet 技能/通用特效，特效播放
  不反向决定伤害结果。
- 敌方总生命达到配置阈值后才显示右上角“逃生”；页面没有二倍速入口。
- 浏览器进入后台时暂停战斗 tick，回到前台后从原 Snapshot 继续，不补算后台 tick。

## 5. 结算与原子保存

| 结果 | 保存内容 | 去向 |
|---|---|---|
| 胜利成立 | 立即原子保存修士生命/阵亡、队伍移除阵亡者、敌人完成态和 `200` 魂晶 | 留在战利品弹窗 |
| 全部拾取 | 校验幸存队伍负重，通过后单独保存临时掉落 | 返回地图 |
| 离开 | 不写入待拾取物；胜利完成态保持不变 | 返回地图 |
| 逃生 | 修士当前生命/阵亡、队伍移除阵亡者；不完成敌人、不发掉落 | 返回地图 |
| 战败 | 复用全队阵亡结算，修士进入还魂殿，按 D0 损失规则处理物品 | 返回营地 |
| 僵持 | 保存存活修士当前生命，不完成敌人、不发掉落 | 返回地图 |

胜利成立后先通过 `prepareVictory` 保存敌人完成态和修士战后状态，再展示二级战利品弹窗：
上半区读取 `temporaryLoot`，下半区读取当前遭遇配置掉落。“全部拾取”以战斗结束后的幸存
队伍计算负重上限；超重只提示并保留弹窗。点击上半区物品每次经 Service 丢弃 `1` 个并
保存，保存失败回滚该次丢弃。“离开”放弃待拾取物。魂晶奖励来自遭遇配置，胜利成立时
自动入账且不占负重；弹窗显示“魂晶 +200（已获得）”，不受普通战利品拾取或放弃影响。

保存失败时，修士生命、阵亡状态、队伍槽位、入山成员、敌人完成态和掉落全部回滚；结果
面板保留并允许重试。胜利完成结算后地图不再弹出同一敌人的事件面板，也不再绘制其标记。

战斗会话本身不进入存档。战斗尚未胜利时刷新，会回到已有入山进度的地图并可重新迎战，
不会保存半场伤害；胜利弹窗出现后刷新按“离开”处理未拾取物，但敌人完成态和修士战后
状态已经保存，同一次入山内重新进入地图不会刷新该敌人。结束入山后重新启程会刷新普通野外敌人。
弹窗中的主动丢弃会立即保存。

## 6. 人工验收

以下验证由用户在 Cocos Creator 与浏览器中操作：

1. 刷新资源后确认新增脚本和 `combat_d0.json` 已生成 `.meta`，控制台无导入错误。
2. 新档完成入山整备，移动到残禁石傀，点击“迎战”进入全屏灰盒战斗。
3. 确认四名修士和一名敌人的名称、生命条、行动条、状态与数字表现可见。
4. 让两名手动修士先后就绪，确认第一人的三个技能保持显示，第二人排队且行动条保持就绪；
   第一人施法后才轮到第二人。再点击名称验收自动施法。
5. 敌方生命达到阈值前不显示“逃生”，达到后出现且可返回地图。
6. 胜利后确认上半区显示当前野外背包、下半区显示“魂晶 +200（已获得）”和 1 个辟谷饼；
   “全部拾取”后返回地图且背包增加，选择“离开”则不增加普通战利品，但魂晶仍已入账。
7. 人为占满负重后点击“全部拾取”，确认提示负重不足且弹窗保留；点击背包物品后数量每次
   减少 1、负重同步下降，再次拾取可成功。
8. 验收战败返回营地及还魂殿状态；刷新后结果不重复结算。
9. 战斗中切到后台再回来，确认时间轴从原进度继续且没有后台瞬间补算。
