# 《昆吾禁地》技术实现方案

版本：0.3  
日期：2026-08-02  
目标：竖屏 2D、Web 首发、单机数据优先、后续可封装至桌面与移动端的玩法 Demo 与 MVP

> IP 边界：本文中的“昆吾山、万修之门、昆吾殿、灵宝阁、镇魔塔”等名称仅用于内部原型和授权版设计说明。未取得《凡人修仙传》相关权利人的书面授权前，不得以这些专有名称、剧情、人物或法宝进行公开发行、商业宣传、众筹或收费测试。代码和数据统一使用中性 ID，发行时可切换为原创名称。

## 1. 技术目标

本项目不是动作游戏，而是由三种交互形态组成：

1. 山外营地：建筑菜单、资源生产、招募、培养、装备、NPC 对话。
2. 禁地方格地图：竖屏俯视、四方向逐格移动、迷雾、补给与负重管理。
3. 半自动战斗：四人小队，依靠职业搭配、装备、技能策略和手动技能时机取胜。

Demo 的技术成功标准：

- Chrome、Edge、Firefox 和移动端主流浏览器中稳定运行，画布按 9:16 自适应；设计分辨率为 1080×1920，可缩放到 720×1280。
- 冷启动进入营地不超过 5 秒，中端电脑战斗维持 60 FPS。
- 完成“营地生产 → 招募 → 编队 → 探索 → 战斗 → 回城结算”闭环。
- 底层支持 5 张完整大地图、6 个初始职业和 12 条一转路线；Demo 实装地图 1、地图 2 的局部内容、6 个初始职业及剑修的两条一转路线，并包含 8 个敌人、3 类 Boss 和 30 件物品。
- 所有数值从数据文件读取，不在界面或战斗代码中硬编码。
- 存档可升级、可校验，异常退出不损坏主存档。
- Web 首次下载的压缩资源目标小于 25 MB，进入可操作状态前不加载未使用章节的大图集和音频。

## 2. Unity、Cocos Creator、Godot 对比

| 维度 | Unity | Cocos Creator | Godot |

| 学习和迭代 | 功能多、工程管理成熟，编辑器较重 | Web 开发者上手快 | 小团队迭代快，节点/场景结构清晰 |
| 授权与成本 | 需持续关注 Unity 商业条款和版本政策 | 引擎开源；云服务和第三方服务另行评估 | MIT，无版税；发行时保留许可证声明 |
| 主机平台 | 官方商业生态成熟 | 弱 | 依赖获批后的第三方移植商 |
| 本项目适配度（Web 首发） | 6.5/10 | 9/10 | 8/10 |

### 2.1 结论

主选 **Cocos Creator 3.8 LTS + TypeScript + WebGL**。

原因：

- Cocos Creator 的 Web Mobile 构建原生支持竖屏铺满浏览器，TypeScript 代码直接进入浏览器运行路径。
- Asset Bundle 能把场景、贴图、脚本和音频按地图拆包，首屏只加载营地与地图 1，未来增加第 6–30 张地图时不会线性放大首次下载。
- UI、Sprite、Animation、TiledMap、ParticleSystem2D 和自定义材质足以覆盖纯 2D 像素项目。
- TypeScript 便于写数据 Schema、领域模型、浏览器 IndexedDB 存档和 Web Shell 集成。
- 现有 PNG、Aseprite、Tiled 与字体素材可直接进入 Cocos Creator 工作流。

下列情况应改选 Unity：

- 首发即包含主机平台。
- 确定采用 Spine/Live2D 大量骨骼动画并需要成熟商业支持。
- 团队已有稳定 Unity/C# 代码库和 CI/CD。
- 需要接入多个国内商业 SDK，且供应商只提供 Unity 插件。

下列情况可以改回 Godot：

- 团队更熟悉 GDScript 和 Godot 场景节点。
- Web 只是短期 Demo，正式版明确转向 PC/Steam 单机。
- 不需要按地图远程分包，也不接浏览器账号、支付或网页容器。

本项目的“Web”指标准浏览器 Web Mobile 构建，不等同于微信小游戏。不过选用 Cocos Creator 后，未来转小游戏平台的迁移成本也低于 Godot。

参考：[Cocos Creator 3.8 LTS 文档](https://docs.cocos.com/creator/3.8/manual/zh/)、[发布到 Web](https://docs.cocos.com/creator/3.8/manual/en/editor/publish/publish-web.html)、[Asset Bundle](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)、[Godot Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)、[Unity 2D 文档](https://docs.unity3d.com/Manual/Unity2D.html)

## 3. 平台与画面技术规格

### 3.1 平台顺序

1. Demo：桌面 Chrome/Edge Web。
2. MVP：响应式 Web + PWA，兼容桌面与 Android 浏览器。
3. 商业版：视运营需求封装 Windows/Android；Steam 和 iOS另行评估。
4. 微信小游戏、主机和原生支付不纳入 MVP。

### 3.2 显示规格

- 设计画布：1080×1920，9:16。
- UI 设计稿与 Web 外层可视窗口：375×817。该比例只定义可视视窗，内部大厅全景仍是可横滑的宽内容。
- 像素游戏内部参考画布：360×640，最终整数倍放大 3 倍。
- 桌面浏览器：游戏容器保持375:817并在窗口中居中，高度优先占满，宽度按比例计算，视窗外使用纯黑页面背景。
- 移动浏览器：同样保持375:817并在可用视口内等比缩放；继续处理刘海、底部手势区和地址栏伸缩。
- Web Shell 只改变外层可视窗口，不得缩放大厅全景内容宽度；大厅、地图等超宽内容由 Cocos 内部 ScrollView/横滑逻辑展示。
- 世界 Tile：16×16 像素；逻辑显示为 48×48 屏幕像素。
- 探索人物：32×32 或 48×48 源帧。
- 战斗人物：48×48 至 96×96 源帧。
- 纹理过滤：Nearest；禁止对 Pixel Art 开启线性过滤。
- UI 安全区：左右各 36 px，上下各 54 px，并适配刘海屏。
- 默认 60 FPS；后台或低电模式允许 30 FPS。

### 3.3 Web 构建约束

- 构建目标使用 Cocos Creator `Web Mobile`，方向设为 Portrait。
- 渲染后端使用成熟的 WebGL 路径；不把实验性 WebGPU 作为首发依赖。
- 逻辑默认运行在主线程；大规模数值模拟确有性能问题时再引入 Web Worker，不预先增加跨线程复杂度。
- 正式地址必须使用 HTTPS。
- 浏览器切换后台时暂停渲染和战斗表现，但领域计时使用可信时间补算。
- 页面缩放、横竖屏变化和浏览器地址栏伸缩不得改变游戏逻辑坐标。
- Web 容器显示加载进度、版本号、静音按钮、全屏按钮、存档导入/导出。
- 不直接修改每次构建生成的 HTML；使用自定义构建模板管理 Web Shell。

### 3.4 Web 发布产物

```text
dist/web/
├─ index.html
├─ application.js
├─ cocos-js/
├─ src/
├─ assets/
├─ remote/
├─ manifest.webmanifest / service worker（项目自建 PWA）
└─ legal/
```

静态托管需设置正确 MIME 类型、缓存策略和 HTTPS。带哈希的版本资源使用长缓存，`index.html` 和版本清单不使用长缓存。

### 3.5 Asset Bundle 分包

```text
start-scene：启动页、加载 UI、最小字体
shared：通用 UI、资源图标、四人战斗公共组件
camp：山外营地与七座建筑
map_01：地图 1 的 Tile、敌人、音乐、事件
map_02 ... map_05：各自独立
career_base：六个初始职业
career_tier_1：十二个一转职业
```

- 首屏只包含 `start-scene`、必要的 `shared` 和营地最小资源。
- 进入营地后后台预载 `map_01`。
- 玩家接近地图出口时预载目标地图 Bundle；地图 2 的隐藏出口满足条件后才预载地图 4。
- 后续第 6–30 张地图采用相同规则，无需进入主包。
- Bundle 使用版本 Hash，构建后上传新版本时保留上一版本一段时间，避免 HTML 与远程资源短暂不一致。
- 地图 Bundle 之间不直接引用脚本；共享脚本放入主代码或 `shared`，避免远程脚本加载顺序问题。

## 5. 核心领域模型

```text
Profile
├─ Wallet：灵粮、灵木、玄铁、灵晶、庚精、灵石、魂晶
├─ CampState：建筑等级、工匠分配、生产结算点
```

为兼容既有存档，`Wallet.spiritStone` 的产品显示名为“灵晶”，`Wallet.immortalCoin` 的产品显示名为“灵石”；字段名不随显示名迁移。

静态定义与运行实例分开：

- `HeroDefinition`：职业、成长曲线、技能池、动画集。
- `HeroInstance`：唯一 ID、资质、等级、境界、随机属性、装备。
- `CareerDefinition`：初始职业、七维成长权重、基础三技能。
- `CareerNodeDefinition`：转职条件、父职业、替换后的三技能、后续转职节点。
- `ItemDefinition`：名称键、图标、类型、堆叠上限。
- `EquipmentInstance`：词条、耐久（若启用）、强化级别。
- `MapDefinition`：尺寸、图块、POI、出生点、遭遇表。
- `ExpeditionState`：某次入山中已揭露格、当前补给和临时掉落。

## 7. 营地与离线生产

生产只记录状态，不每 30 秒永久运行一个 Timer。

结算公式：

```text
有效秒数 = clamp(当前服务器/本地可信时间 - 上次结算时间, 0, 离线上限)
周期数 = floor(有效秒数 / 当前生产周期)
实际产量 = 周期数 × 岗位人数 × 单周期产量 × 增益
灵粮净变化 = 灵粮产出 - 其他岗位灵粮维护
```

实现要求：

- Demo 使用本地 UTC；检测系统时间倒退，大于 5 分钟时暂停离线收益并提示。
- MVP 若无服务器，将离线上限设为 8 小时，避免改系统时间无限刷资源。
- 每次进入营地、修改工匠、退出游戏时结算。
- 先结算旧配置，再保存新分配，防止切换岗位吞产量。
- 资源使用 64 位整数；所有乘法在整数域完成。

## 8. 酒馆/招贤台

刷新状态包括：

```text
offers[3]
next_free_refresh_at
manual_refresh_count_in_cycle
refresh_seed
```

- 三个栏位由确定性随机种子生成，重启游戏不能反复读档刷结果。
- 免费刷新到点时生成新种子并把手动刷新次数清零。
- 招募后对应栏位标记为空，不立刻补位。
- “灵粮招募”只在新手阶段开放，且池中不出现高资质。
- Demo 不接充值；高级货币只保留数据结构，不提供商店入口。

## 9. 方格地图与迷雾

### 9.1 坐标与移动

- 使用自定义不可变 `GridCoord { x: number; y: number }`，不把世界像素坐标与格子坐标混用。
- 四方向移动，不允许斜走。
- Tile 数据存地形、阻挡、移动消耗、危险度、视觉标签。
- 寻路使用 A*；长按目的地只在已知可行走格中寻路。
- 每走一步按地形扣除灵粮，并检查遭遇、POI、负重和队伍状态。
- 灵粮归零后仍由领域层持久推进四步衰竭计数；第 4 步先保存移动结果，表现结束后
  原子结算全队阵亡，表现层不得自行修改修士存活状态。
- 每张野外地图是一张完整开放大图，不由“主路径/支路”组成；队伍只占其中一个格子。
- 敌人、资源、副本入口、剧情事件、Boss 与跨图出口均有固定坐标。
- 被击败、采集或完成后的固定对象记录自身状态；若允许刷新，也只在原固定坐标刷新。
- 地图可以存在多个跨图出口。例如地图 2 的普通出口通往地图 3，隐藏出口在满足高属性检定和任务道具后直接通往地图 4。

### 9.2 迷雾状态

每格三态：

1. `UNKNOWN`：完全黑暗，不显示内容。
2. `DISCOVERED`：曾经看过，显示暗化地形，不显示动态怪物。
3. `VISIBLE`：当前神识/探灵灯范围内，显示完整内容。

视野采用整数圆：

```text
dx² + dy² <= radius²
```

基础半径 2，探灵灯升级后为 3/4/5。障碍物是否遮挡视线在 MVP 后实现；Demo 仅使用半径。

### 9.3 地图存档压缩

- 小地图直接使用位数组保存已探索格。
- 动态对象只保存与初始定义不同的状态，如“宝箱已开”“Boss 已死”。
- 固定对象使用 `map_id + object_id` 保存；不得依赖随机种子重排位置。
- 同一地图的主线 Boss、支线 Boss、野外 Boss 使用不同状态字段和刷新规则。

### 9.4 探索属性检定

七维属性为力量、魔力、技巧、速度、体质、护甲、抗性。探索事件主要检定前三维，但数据结构允许使用任意属性。

聚合方式：

- `SUM`：四人属性总和。
- `MAX`：队内最高单人属性。
- `COUNT`：达到单人门槛的人数。
- `ALL`：每名存活成员都达到门槛。

```json
{
  "check_id": "check_map02_small_ruin_technique",
  "attribute": "technique",
  "aggregate": "SUM",
  "threshold": 30,
  "on_success": [{"type": "open_event", "id": "event_safe_route"}],
  "on_failure": [{"type": "party_hp_percent", "value": -20}]
}
```

检定结果由领域层结算，地图 UI 只展示需求和结果。百分比掉血至少保留 1 点生命，除非事件文字明确说明可能致死。

## 10. 战斗架构

战斗采用固定时间步模拟，显示与模拟分离：

- 模拟 Tick：20 Hz。
- 渲染：60 FPS。
- 战斗单位最多 4 名友方、6 名普通敌人或 1 名大型 Boss + 2 个召唤物。
- 所有技能先生成 `CombatCommand`，再由结算器处理。

结算顺序：

```text
读取行动意图
→ 检查控制与资源
→ 选择目标
→ 命中/暴击
→ 伤害或治疗
→ 附加状态
→ 触发被动与反击
→ 生成表现事件
→ 死亡检查
```

核心接口：

```typescript
export interface CombatCommand {
  actorId: number;
  skillId: string;
  targetIds: number[];
}

export interface CombatEvent {
  type: string;
  payload: Readonly<Record<string, unknown>>;
}
```

动画和特效只消费 `CombatEvent`，不得反向决定伤害结果。这样可以加速战斗、跳过动画、战斗回放和自动化测试。

### 10.1 七维属性结算

```text
生命上限 = 职业基础生命 + 体质 × 生命系数 + 装备生命
物理技能基值 = 力量 × 力量倍率 + 技巧 × 技巧副倍率
法术技能基值 = 魔力 × 魔力倍率 + 技巧 × 技巧副倍率
行动间隔 = clamp(技能基础间隔 × 100 / (100 + 速度), 最小间隔, 最大间隔)
物理减伤率 = 护甲 / (护甲 + 等级常数)
法术减伤率 = 抗性 / (抗性 + 等级常数)
```

每个技能明确声明依赖属性，不能根据职业名称在代码中推断。

### 10.2 转职数据

- 每个职业节点始终提供 3 个主动技能槽。
- 转职不是在旧技能上无限追加，而是进入新职业节点，并由该节点定义新的三技能。
- 可以保留“技能继承”字段，但 MVP 默认只允许继承一个被动特性，不允许自由拼装全部旧技能。
- 转职树按父 ID 组织，核心代码不限制层数；MVP 实装初始职业和第一次分支，后续可继续增加二转、三转。

## 11. AI 与技能策略

修士使用规则列表：

```text
若最低友方生命 < 35% → 单体治疗
若友方存活数 ≥ 3 且平均生命 < 60% → 群体治疗
若敌方有护盾 → 破法
否则 → 普攻
```

敌人使用轻量状态机：

- Idle
- ChooseAction
- Cast
- Recover
- Disabled
- Dead

Boss 额外使用按生命百分比和回合时间驱动的阶段脚本，不做通用行为树。

### 11.1 无前后排目标选择

- 四名队员在规则上没有前排和后排。
- 普通单体攻击从所有存活目标中按权重选择。
- 嘲讽生效时，遵守嘲讽的单体技能强制选择嘲讽者。
- 群体技能、随机多段技能以及标记为 `ignore_taunt` 的技能不受嘲讽影响。
- 若同时存在多个嘲讽者，则选择嘲讽强度最高者；相同强度再随机。
- 美术上的左右站位只用于防止重叠，不参与命中概率和承伤。

## 12. UI 架构

- 页面层：营地、建筑、地图、战斗。
- 模态层：入山整备（编队/装载/地图选择）、确认、掉落、角色详情、教程。
- 全局层：资源栏、Toast、加载遮罩、网络/存档错误。
- 所有页面采用 Presenter/ViewModel，把格式化逻辑与领域模型隔离。
- 按钮最小触控尺寸 48×48 dp。
- 关键操作必须二次确认：解雇高资质修士、消耗高级货币、覆盖存档。
- 颜色不是唯一信息载体；灵根资质同时使用边框形状和文字。

### 12.1 API First 与前后端边界

新需求和被修改的旧页面统一按未来存在独立服务端设计，客户端固定调用链为：

```text
Presenter → Application Service → API Port
          → Local Adapter（当前）/ HTTP Adapter（未来）
          → Response → Service 更新 GameState、持久化并发出应用事件
          → Presenter 刷新 ViewModel
```

- Presenter 只管理页面生命周期、用户意图和 ViewModel 渲染，不读写 `GameState`、
  不拼装服务端 DTO，不直接调用 `fetch`。
- API Port、请求/响应 DTO 和错误类型独立于 HTTP；Local Adapter 与 HTTP Adapter
  实现同一 Port，通过 Composition Root 注入。
- Local Adapter 保持异步 `Promise` 语义，并可模拟业务失败、超时、断网和冲突；
  它不操作 Cocos 节点，也不绕过 Application Service 修改客户端权威镜像。
- 账号、付费货币、交易、排行榜和联网战斗结算默认服务端权威；页面开关、
  动画、音效和本地展示偏好由客户端负责。
- 进入实现前必须同步产出并互相链接：客户端技术设计、服务端技术设计、
  API 契约、Local Adapter 实现与正常/超时/断网/重复提交/冲突/失败恢复验收清单。

## 13. 存档与版本迁移

存档使用浏览器 IndexedDB：

```text
Database: kunwu_game
Object stores:
├─ profiles
├─ backups
├─ settings
└─ telemetry_local
```

用户清理网站数据、无痕模式退出或浏览器回收存储空间都可能导致存档丢失，因此必须提供手动导出/导入：

- 导出：生成带版本与校验的 `.kwsave` 文件并由浏览器下载。
- 导入：文件选择器读取、校验、预览档案时间后覆盖。
- PWA 首次安装后请求持久存储权限；不能假设浏览器一定批准。

写入流程：

1. 序列化并计算 SHA-256 或 HMAC 校验。
2. 将旧主档内容写入 `.bak`。
3. 在同一个 IndexedDB transaction 中写入新主档。
4. 加载失败时自动尝试备份并记录错误。

顶层字段：

```json
{
  "schema_version": 3,
  "game_version": "0.1.0",
  "saved_at_utc": 1785330000,
  "checksum": "...",
  "payload": {}
}
```

每次改变 Schema 都新增迁移函数，不直接修改历史迁移。

## 14. 音频、动画与特效接入

- 音频总线：Master、Music、Ambient、SFX、UI。
- 动画通过 Cocos `Animation`、`AnimationClip` 和 SpriteFrame 事件，技能命中帧发出表现信号。
- 粒子与屏幕震动由 `VfxService` 统一创建并池化。
- 不允许技能脚本直接加载路径；从 `EffectDefinition` 查询表现资源。
- 低画质关闭环境粒子、热扭曲和部分动态光。

- 所有核心数值有自动测试。
- Web Demo 可在桌面主流浏览器完成 30–45 分钟垂直切片。
- 不联网也能完成全部 MVP 内容。
- 首次联网加载后，PWA 模式可在缓存未被清理时离线启动。
- 授权名与原创名通过本地化表切换，不影响存档 ID。
- Credits 包含 Cocos Creator/引擎要求的声明与全部第三方素材许可。
