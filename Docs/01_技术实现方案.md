# 《昆吾禁地》技术实现方案

版本：0.1  
日期：2026-07-29  
目标：竖屏 2D、单机优先、可扩展至 Android/iOS/Steam 的玩法 Demo 与 MVP

> IP 边界：本文中的“昆吾山、万修之门、昆吾殿、灵宝阁、镇魔塔”等名称仅用于内部原型和授权版设计说明。未取得《凡人修仙传》相关权利人的书面授权前，不得以这些专有名称、剧情、人物或法宝进行公开发行、商业宣传、众筹或收费测试。代码和数据统一使用中性 ID，发行时可切换为原创名称。

## 1. 技术目标

本项目不是动作游戏，而是由三种交互形态组成：

1. 山外营地：建筑菜单、资源生产、招募、培养、装备、NPC 对话。
2. 禁地方格地图：竖屏俯视、四方向逐格移动、迷雾、补给与负重管理。
3. 半自动战斗：四人小队，依靠职业搭配、装备、技能策略和手动技能时机取胜。

Demo 的技术成功标准：

- Windows 上稳定运行，1080×1920 竖屏逻辑分辨率，可缩放到 720×1280。
- 冷启动进入营地不超过 5 秒，中端电脑战斗维持 60 FPS。
- 完成“营地生产 → 招募 → 编队 → 探索 → 战斗 → 回城结算”闭环。
- 至少支持一张 40×60 方格地图、4 个职业、8 个敌人、1 个 Boss、30 件物品。
- 所有数值从数据文件读取，不在界面或战斗代码中硬编码。
- 存档可升级、可校验，异常退出不损坏主存档。

## 2. Unity、Cocos Creator、Godot 对比

| 维度 | Unity | Cocos Creator | Godot |
|---|---|---|---|
| 主要语言 | C# | TypeScript | GDScript / C# / C++ |
| 2D 工作流 | 完整，Tilemap、2D Animation、URP 2D 成熟 | 轻量，UI 与移动端 2D 高效 | 原生 2D 节点体系，TileMapLayer、动画、粒子直接 |
| 竖屏 UI | 成熟，工具与插件多 | 很强，接近前端开发体验 | 足够，Control/Container 需要团队建立规范 |
| 包体与启动 | 相对较重 | 较轻 | 较轻 |
| 移动端/小游戏 | Android/iOS 成熟；小游戏常依赖第三方方案 | 微信等小游戏生态更顺手 | Android/iOS 可用；国内小游戏适配成本较高 |
| PC/Steam | 很强 | 可行但不是主战场 | 很合适 |
| 动画生态 | Spine、Live2D、DragonBones 等集成成熟 | Spine/DragonBones/帧动画便利 | 帧动画与骨骼动画够用，商业中间件支持弱于 Unity |
| 特效 | URP 2D、Shader Graph、VFX 生态强 | 2D 粒子、材质够用 | GPUParticles2D、CanvasItem Shader 足够本项目 |
| 商店/插件 | 最大 | 国内移动端资源较多 | 社区插件较少，质量差异较大 |
| 学习和迭代 | 功能多、工程管理成熟，编辑器较重 | Web 开发者上手快 | 小团队迭代快，节点/场景结构清晰 |
| 授权与成本 | 需持续关注 Unity 商业条款和版本政策 | 引擎开源，周边服务另行评估 | MIT，无版税；发行时保留许可证声明 |
| 主机平台 | 官方商业生态成熟 | 弱 | 依赖获批后的第三方移植商 |
| 本项目适配度 | 8/10 | 7/10 | 9/10 |

### 2.1 结论

主选 **Godot 4.7.x + GDScript**。

原因：

- 项目是纯 2D、像素风、单机数据驱动，小团队不需要 Unity 的完整 3D 与大型商业插件生态。
- Godot 的场景、节点、信号非常适合把建筑、地图格、战斗单位和 UI 拆成可复用模块。
- MIT 许可没有版税，原型成本和长期许可不确定性最低。发行时在 Credits/许可证页面保留 Godot 声明即可。
- GDScript 在 Godot 4 的桌面、移动、Web 导出路径最统一；如果采用 C#，Web 平台存在额外限制。
- 现有素材均为 PNG、Aseprite、Tiled 等 2D 资源，可直接进入 Godot 工作流。

下列情况应改选 Unity：

- 首发即包含主机平台。
- 确定采用 Spine/Live2D 大量骨骼动画并需要成熟商业支持。
- 团队已有稳定 Unity/C# 代码库和 CI/CD。
- 需要接入多个国内商业 SDK，且供应商只提供 Unity 插件。

下列情况应改选 Cocos Creator：

- 微信小游戏是第一优先级。
- 团队主体是 TypeScript/Web 工程师。
- 产品更偏长线移动端运营，且已有成熟的小游戏热更、支付与账号体系。

参考：[Godot 许可](https://godotengine.org/license/)、[Godot 官方站与当前版本](https://godotengine.org/)、[Unity 2D 文档](https://docs.unity3d.com/Manual/Unity2D.html)、[Cocos Creator 文档](https://docs.cocos.com/creator/manual/zh/)

## 3. 平台与画面技术规格

### 3.1 平台顺序

1. Demo：Windows x64。
2. MVP：Windows + Android。
3. 商业版：Steam Windows，验证收益后再评估 iOS。
4. 主机与小游戏不纳入 MVP。

### 3.2 显示规格

- 设计画布：1080×1920，9:16。
- 像素游戏内部参考画布：360×640，最终整数倍放大 3 倍。
- 世界 Tile：16×16 像素；逻辑显示为 48×48 屏幕像素。
- 探索人物：32×32 或 48×48 源帧。
- 战斗人物：48×48 至 96×96 源帧。
- 纹理过滤：Nearest；禁止对 Pixel Art 开启线性过滤。
- UI 安全区：左右各 36 px，上下各 54 px，并适配刘海屏。
- 默认 60 FPS；后台或低电模式允许 30 FPS。

### 4.1 Autoload 单例

| 单例 | 职责 | 禁止承担的职责 |
|---|---|---|
| `App` | 场景切换、全局生命周期 | 存放所有游戏数据 |
| `GameState` | 当前存档的聚合状态 | 直接操作 UI |
| `DataRegistry` | 加载静态表并提供只读查询 | 修改玩家存档 |
| `SaveService` | 原子写入、备份、版本迁移 | 业务计算 |
| `EventBus` | 跨场景领域事件 | 高频逐帧广播 |

| `TimeService` | UTC 时间、离线收益、防回拨策略 | 直接发奖励 |
| `SceneRouter` | 页面堆栈、过渡、返回规则 | 业务状态 |

业务逻辑尽量写成普通 `RefCounted`/Resource 类，由场景节点调用。避免把整个项目堆进全局单例。

## 5. 核心领域模型

```text
Profile
├─ Wallet：灵粮、灵木、玄铁、灵石、庚精、仙铢、魂晶
├─ CampState：建筑等级、工匠分配、生产结算点
├─ Roster：修士实例、等级、境界、装备、伤亡状态
├─ Inventory：道具堆叠、装备实例
├─ StoryState：章节、任务、NPC、设施解锁
├─ ExpeditionState：地图、坐标、补给、负重、迷雾、临时战利品
└─ Settings：语言、音量、振动、画质、辅助选项
```

静态定义与运行实例分开：

- `HeroDefinition`：职业、成长曲线、技能池、动画集。
- `HeroInstance`：唯一 ID、资质、等级、境界、随机属性、装备。
- `ItemDefinition`：名称键、图标、类型、堆叠上限。
- `EquipmentInstance`：词条、耐久（若启用）、强化级别。
- `MapDefinition`：尺寸、图块、POI、出生点、遭遇表。
- `ExpeditionState`：某次出征中已揭露格、当前补给和临时掉落。

## 6. 数据驱动

策划主表使用 CSV，复杂嵌套配置使用 JSON；导入时转换为 Godot Resource 或只读字典。正式版构建前执行 Schema 校验。

建议主表：

| 表 | 主键示例 | 关键字段 |
|---|---|---|
| `heroes.csv` | `hero_sword_001` | 职业、资质权重、成长、动画集 |
| `skills.csv` | `skill_sword_pierce` | 冷却、目标规则、倍率、效果 ID |
| `buildings.csv` | `camp_recruit_hall` | 等级、成本、解锁、功能参数 |
| `items.csv` | `mat_spirit_wood` | 类型、品质、堆叠、售价 |
| `recipes.csv` | `recipe_blade_t1` | 输入、输出、工坊等级 |


## 7. 营地与离线生产

生产只记录状态，不每 30 秒永久运行一个 Timer。

结算公式：

```text
有效秒数 = clamp(当前服务器/本地可信时间 - 上次结算时间, 0, 离线上限)
周期数 = floor(有效秒数 / 当前生产周期)
实际产量 = 周期数 × 岗位人数 × 单周期产量 × 增益
食物净变化 = 食物产出 - 其他岗位食物维护
```

实现要求：

- Demo 使用本地 UTC；检测系统时间倒退，大于 5 分钟时暂停离线收益并提示。
- MVP 若无服务器，将离线上限设为 8 小时，避免改系统时间无限刷资源。
- 每次进入营地、修改工匠、退出游戏时结算。
- 先结算旧配置，再保存新分配，防止切换岗位吞产量。
- 资源使用 64 位整数；所有乘法在整数域完成。

## 8. 酒馆/招贤台

刷新状态包括：

```text
offers[3]
next_free_refresh_at
manual_refresh_count_in_cycle
refresh_seed
```

- 三个栏位由确定性随机种子生成，重启游戏不能反复读档刷结果。
- 免费刷新到点时生成新种子并把手动刷新次数清零。
- 招募后对应栏位标记为空，不立刻补位。
- “灵粮招募”只在新手阶段开放，且池中不出现高资质。
- Demo 不接充值；高级货币只保留数据结构，不提供商店入口。

## 9. 方格地图与迷雾

### 9.1 坐标与移动

- 使用 `Vector2i`。
- 四方向移动，不允许斜走。
- Tile 数据存地形、阻挡、移动消耗、危险度、视觉标签。
- 寻路使用 A*；长按目的地只在已知可行走格中寻路。
- 每走一步按地形扣除灵粮，并检查遭遇、POI、负重和队伍状态。

### 9.2 迷雾状态

每格三态：

1. `UNKNOWN`：完全黑暗，不显示内容。
2. `DISCOVERED`：曾经看过，显示暗化地形，不显示动态怪物。
3. `VISIBLE`：当前神识/探灵灯范围内，显示完整内容。

视野采用整数圆：

```text
dx² + dy² <= radius²
```

基础半径 2，探灵灯升级后为 3/4/5。障碍物是否遮挡视线在 MVP 后实现；Demo 仅使用半径。

### 9.3 地图存档压缩

- 小地图直接使用位数组保存已探索格。
- 动态对象只保存与初始定义不同的状态，如“宝箱已开”“Boss 已死”。
- 临时怪物由地图种子和进入次数生成。

## 10. 战斗架构

战斗采用固定时间步模拟，显示与模拟分离：

- 模拟 Tick：20 Hz。
- 渲染：60 FPS。
- 战斗单位最多 4 名友方、6 名普通敌人或 1 名大型 Boss + 2 个召唤物。
- 所有技能先生成 `CombatCommand`，再由结算器处理。

结算顺序：

```text
读取行动意图
→ 检查控制与资源
→ 选择目标
→ 命中/暴击
→ 伤害或治疗
→ 附加状态
→ 触发被动与反击
→ 生成表现事件
→ 死亡检查
```

核心接口：

```gdscript
class_name CombatCommand
var actor_id: int
var skill_id: StringName
var target_ids: Array[int]

class_name CombatEvent
var type: StringName
var payload: Dictionary
```

动画和特效只消费 `CombatEvent`，不得反向决定伤害结果。这样可以加速战斗、跳过动画、战斗回放和自动化测试。

## 11. AI 与技能策略

英雄使用规则列表：

```text
若最低友方生命 < 35% → 单体治疗
若友方存活数 ≥ 3 且平均生命 < 60% → 群体治疗
若敌方有护盾 → 破法
否则 → 普攻
```

敌人使用轻量状态机：

- Idle
- ChooseAction
- Cast
- Recover
- Disabled
- Dead

Boss 额外使用按生命百分比和回合时间驱动的阶段脚本，不做通用行为树。

## 12. UI 架构

- 页面层：营地、建筑、编队、地图、战斗。
- 模态层：确认、掉落、角色详情、教程。
- 全局层：资源栏、Toast、加载遮罩、网络/存档错误。
- 所有页面采用 Presenter/ViewModel，把格式化逻辑与领域模型隔离。
- 按钮最小触控尺寸 48×48 dp。
- 关键操作必须二次确认：解雇高资质修士、消耗高级货币、覆盖存档。
- 颜色不是唯一信息载体；品级同时使用边框形状和文字。

## 13. 存档与版本迁移

存档文件：

```text
user://save/profile_0.json
user://save/profile_0.bak
user://save/profile_0.tmp
```

写入流程：

1. 序列化到 `.tmp`。
2. 计算 SHA-256 或 HMAC 校验。
3. 成功后将旧主档复制为 `.bak`。
4. 原子替换主档。
5. 加载失败时自动尝试备份并记录错误。

顶层字段：

```json
{
  "schema_version": 3,
  "game_version": "0.1.0",
  "saved_at_utc": 1785330000,
  "checksum": "...",
  "payload": {}
}
```

每次改变 Schema 都新增迁移函数，不直接修改历史迁移。

## 14. 音频、动画与特效接入

- 音频总线：Master、Music、Ambient、SFX、UI。
- 动画通过 `AnimationTree` 或 `AnimatedSprite2D`，技能命中帧发出表现信号。
- 粒子与屏幕震动由 `VfxService` 统一创建并池化。
- 不允许技能脚本直接加载路径；从 `EffectDefinition` 查询表现资源。
- 低画质关闭环境粒子、热扭曲和部分动态光。

## 16. 测试策略

### 16.1 单元测试

- 生产结算与食物不足。
- 酒馆概率和保底。
- 负重与补给扣除。
- 视野半径。
- 伤害、治疗、暴击、状态叠加。
- 掉落权重。
- 存档迁移。

### 16.2 仿真测试

- 运行 10 万次酒馆刷新，误差符合概率区间。
- 运行 1 万场自动战斗，检查死循环和极端胜率。
- 模拟 30 天离线结算，验证上限与时间回拨。
- 随机生成移动路径，保证负补给不能继续行走。

### 16.3 验收设备

- Windows：1080p 集显笔记本。
- Android 低端：4 GB RAM、720p。
- Android 中端：6–8 GB RAM、1080p。

## 19. 技术 Definition of Done

- 新英雄、新技能、新物品、新地图可只改数据和资源，不改核心代码。
- 强制退出后主档可恢复。
- 所有核心数值有自动测试。
- Windows Demo 可完成 30–45 分钟垂直切片。
- 不联网也能完成全部 MVP 内容。
- 授权名与原创名通过本地化表切换，不影响存档 ID。
- Credits 包含 Godot 与全部第三方素材许可。
